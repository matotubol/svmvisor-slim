# FT601 external read transport

**Legacy transport prototype:** the current resident no longer services the physical
mailbox described below, and `xtask live-read` now uses the
[same-PC VMMCALL interface](../../LOCAL-READ.md). FT601 RTL/driver tests remain as
external-host transport groundwork; this is not the active process-reader workflow.

This is an opt-in transport for the Squirrel board's FT601 USB 3.0 FIFO bridge.
It replaces JTAG transfers for the existing bounded physical-read service. It
does not itself implement process subscriptions, periodic sampling, a guest
hypercall interface, DMA, flash programming, or a real-time guarantee.

The default FPGA configuration keeps FT601 disabled. Existing JTAG diagnostics
and recovery remain available. Enabling FT601 requires a new FPGA build; the
currently installed image is not changed by building or running offline tests.

## Architecture

```text
External computer / USB client
    -> FT601 FIFO -> FPGA command slot
    -> CPU reads the slot through PCIe BAR0 during suitable existing VM exits
    -> admitted physical copy in the hypervisor
    -> CPU writes the response through BAR0
    -> FPGA response slot -> FT601 FIFO -> external computer
```

The FPGA does not originate PCIe memory requests. CPU BAR accesses and USB
transfers are separate from device-initiated DMA into target RAM. This design
does not require relaxing IOMMU permissions. Device enumeration, BAR ownership,
cache attributes, reset handling, and coexistence with the installed protection
configuration still require platform validation.

FT601 replaces the transport, not the scheduling mechanism. A request can wait
indefinitely if no suitable VM exit occurs; the host deadline still terminates
the observer session. Future hypervisor-local sampling is a separate change.

The FT601 transfers 32 bits in parallel on each accepted FIFO beat. Its external
data pins are bidirectional: reads and writes require direction arbitration and
turnaround, not simultaneous opposing drivers. Separate acknowledged request and
response buffers decouple USB, board and PCIe clocks; the CPU does not wait for
the external client to consume a response. The first protocol deliberately
allows only one outstanding command. Multiple queued commands and a streaming
ring are later throughput optimizations, not features implied by the parallel
bus or by this implementation.

## Board contract

The pin reference is the pinned Squirrel board support at commit
`c538c4170678c13f723dc921905fb81ff3c71d8e`, under
`target/firmware/upstream/pcileech-fpga-c538c417/PCIeSquirrel/src/`.
The implementation uses a fresh bounded FIFO controller, not the upstream
unbounded receive assumption or dummy-word stream.

The intended bus is the FT601 32-bit synchronous FT245 interface. The board
reference uses a 100 MHz FT601 clock on W19. The chip's actual EEPROM mode,
clock selection, channel configuration, USB endpoints, serial identity, and
electrical timing must match the implementation before a live session. The
client must not silently reprogram EEPROM to obtain a match.

FTDI's advertised 400 MB/s is a maximum FIFO burst capability, not measured
application throughput or a completion-latency guarantee. Source:
[FT600/FT601 datasheet](https://ftdichip.com/wp-content/uploads/2020/07/DS_FT600Q-FT601Q-IC-Datasheet.pdf).

## Wire protocol

Transfers contain fixed 64-byte records: sixteen little-endian 32-bit words,
with no dummy words or implicit byte swapping. Word 15 is reflected CRC32 of
bytes 0 through 59, using polynomial `0xedb88320`, initial value `0xffffffff`,
and final complement. CRC detects corruption; it does not authenticate a peer.

Only one operation may be pending. The host starts with a random nonzero
32-bit sequence and increases it for every operation, including identity
queries. Sequence wrap ends the host session. FPGA duplicate suppression rejects
the immediately preceding sequence; it does not impose a global numerical order
across clean host sessions. The random start provides probabilistic stale-frame
correlation, not authentication. Frames cannot replace an occupied command, and
an ambiguous operation is never automatically replayed.

### Physical read (operation 1)

The request and response are the existing version-1 read-service frames in
[`READ-SERVICE.md`](READ-SERVICE.md). The request magic is `0x51525653` and
response magic is `0x50525653`. The request carries its sequence, length,
guest-physical address and expected nonzero boot identity. One response carries
at most 32 bytes. Existing runtime admission, CRC, sequence, address, status,
length and padding validation remain mandatory.

### Identity (operation 2)

The request uses the same request magic and version. Word 2 is its nonzero
sequence; word 3 is 2; words 4 through 14 are zero; word 15 is the CRC.
This operation is handled by the FPGA and does not request a guest-memory read.

The reply consists of two standard response-format records, each with the
requested sequence, success status, and length 32. Their address fields are 0
and 32 respectively. Their payloads, in that order, contain one coherently
captured 64-byte identity snapshot. Each reply has its own CRC; the assembled
snapshot also retains its existing header and CRC. A zero boot identity is not
a ready runtime. Matching FPGA, ROM and boot identities detect changes, not
authentication or instantaneous global consistency.

The host obtains identity before and after each physical operation and compares
it with the session identity. Responses from the wrong sequence, reordered
identity halves, malformed lengths, invalid CRCs or a changed identity end the
session without delivering sample bytes.

## Failure and reset behavior

An incomplete or corrupt stream must not be recovered by searching for a magic
byte pattern inside arbitrary data. A host timeout, short write, incomplete response, device
disconnect or malformed response poisons that host session. Reopening the USB
handle, draining a pipe, or terminating the client does not prove that an
outstanding hypervisor request was cancelled. A fresh live session therefore
requires an independently established idle/reset state.

Normal completion, USB backpressure, PCIe transaction reset and board-level
reset have different meanings. Tests must verify that no partial frame becomes
a request and no partial CPU response becomes a published USB response. A reset
must not manufacture a successful response to an old request.

Successful partial USB reads are accumulated only up to the exact 64- or
128-byte reply under the original deadline. This is not resynchronization or a
request retry. D3XX pipe abort does not prove that the FPGA command was cancelled;
the complete FTDI out-of-band abort-recovery mechanism is not implemented here.
See [FTDI AN 412](https://ftdichip.com/wp-content/uploads/2020/08/AN_412_FT600_FT601-USB-Bridge-chips-Integration.pdf).
Bench validation must confirm short 64-byte replies and the two-part 128-byte
identity transfer complete with the actual chip configuration and driver.

## Host interface

`ft601_bridge.py` imports no native driver and opens no device until an explicit
live invocation. Offline encoding is available without a board:

```powershell
python -B firmware/card/ft601_bridge.py --encode-identity 0x10203041
```

The live adapter requires native 64-bit Windows Python, an explicitly selected
device serial, and the absolute path and SHA-256 of the reviewed AMD64 FTDI
D3XX DLL. Installations and chip-configuration changes are not performed by the
bridge. Example arguments, to use only after a compatible candidate is deployed
and the device configuration and idle state are established:

```powershell
python -B firmware/card/ft601_bridge.py --live --serial YOUR_SERIAL --dll C:/approved/FTD3XX.dll --dll-sha256 YOUR_DLL_SHA256
```

The bridge's stdin/stdout protocol is compatible with the existing physical
bridge interface. One input line is, for example:

```json
{"id":1,"gpa":"0x100000","length":8,"timeout_ms":1000}
```

A successful reply contains `id`, `status`, hex `data`, `startup_ms` and
`round_trip_ms`. The example address is only a wire-format illustration, not a
verified source on a live machine. `xtask live-read` can select this executable
through its existing `--bridge` and repeated `--bridge-arg` options. Its process
lookup and page-table walking remain outside the hypervisor in this first
transport milestone; USB support does not silently turn them into subscriptions.

Shared golden records are in `tests/ft601_wire_vectors.mem`, in this order:
physical request, physical response, identity request, identity snapshot, first
identity response, second identity response. Rust, Python and RTL tests use
these records to check word order and CRC agreement.

## Validation and deployment boundary

Required offline evidence includes codec agreement, fragmented USB transfers,
short/error transfers, monotonic sequences, before/after identity checks,
backpressure, clock-domain handshakes, partial frames, occupied slots, and
transaction reset. FPGA compilation and timing evidence are separate from
simulation; a simulation pass does not establish electrical timing.

Before hardware deployment, retain the existing recovery image, review the
complete candidate and its source hashes, verify the FT601 chip configuration,
and confirm the board mapping and timing constraints. Programming is a separate
action from offline construction. No firmware has been flashed as part of this
implementation work.

The first hardware measurement should be a known bounded physical read with
startup and request time recorded separately. Process sampling, sustained
throughput, sample age, 60 Hz delivery, and DMA-protection compatibility remain
unverified until tested on the intended platform.
